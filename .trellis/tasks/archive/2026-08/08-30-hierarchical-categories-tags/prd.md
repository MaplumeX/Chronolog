# 分类与标签支持两级层级

## Goal

分类（categories）和标签（tags）支持父子两级层级：现有条目全部保持功能不变的前提下，用户可以将分类/标签组织为最多两层的树（父级 + 子级），并在选择器、管理页与统计中正确呈现。

## 背景与澄清结论（来自用户）

1. **层级深度**：仅两级（父级 + 子级），不需要任意深度。
2. **统计聚合**：统计页支持**切换**——可按「子分类独立显示」或「子分类时长向上汇总到父分类」两种模式切换显示。
3. **删除语义**：级联删除——删除父分类/父标签时，其子级一并删除。子分类/子标签上的时间记录与标签关联随现有外键级联规则处理。
4. **选择限制**：时间记录（time entries）选择分类时**任意层级都可选**（父级、子级均可挂记录）；标签同理。

## Requirements

### 数据模型

- R1: `categories` 与 `tags` 各新增可空的 `parent_id` 字段，指向同表同用户的另一行；`parent_id` 为空表示顶层节点。
- R2: 强制约束层级深度 ≤ 2：任何节点的父节点必须是顶层节点（即不能把已有子节点的节点再设为子级）。该约束需在 API 层校验（SQLite 不便用纯 DDL 表达）。
- R3: 唯一性约束调整：同父级下名字唯一（`(user_id, parent_id, name)`），不同父级下允许重名。迁移需兼容既有 `(user_id, name)` 唯一数据。
- R4: 迁移对存量数据零破坏：所有现有分类/标签保持为顶层节点，功能不变。

### API

- R5: 分类与标签的 CRUD API 支持 `parentId`（创建/更新时可指定父级，置空表示提升为顶层）。
- R6: 删除父级节点时级联删除其子节点（级联语义明确返回成功）。
- R7: 修改父级/名称时应用 R2 的深度校验与 R3 的同父重名校验，返回明确错误。
- R8: 引用分类/标签的既有 API（entries 创建/编辑、goals、stats、today）行为兼容：仍以节点 id 引用，不因层级引入破坏性变更。

### 前端

- R9: 分类页与标签页管理界面以两级树展示，支持创建子级、拖拽或显式操作改变父子关系（方式由 design 决定，满足可操作即可）、重命名、调色、删除（删除父级需确认级联后果）。
- R10: `CategoryPicker` / `TagPicker` 选择器以分组/缩进方式呈现两级结构；所有层级节点均可被选中挂到时间记录上。
- R11: 统计页（today / stats-range）提供聚合模式切换：独立模式（默认，行为与现状一致）与汇总模式（子级时长并入父级显示）。切换仅影响展示，不改变数据。

### 兼容性

- R12: 既有客户端 API 消费方（API token 脚本等）不因响应结构变化而破坏——列表接口新增 `parentId` 字段是加法变更，允许。
- R13: 默认分类（DEFAULT_CATEGORIES）保持顶层创建。

## Out of Scope

- 任意深度层级（>2 层）
- 跨层级统计钻取交互（只做汇总/独立两种模式）
- 分类/标签排序自定义

## Acceptance Criteria

- [ ] AC1: 迁移后存量分类/标签全部为顶层节点，现有记录、goals、统计不受影响（回归通过）。
- [ ] AC2: 可创建子分类/子标签；尝试给已有子节点的节点再挂子级被拒绝并返回明确错误（R2）。
- [ ] AC3: 同一父级下重名被拒绝；不同父级下允许重名（R3）。
- [ ] AC4: 删除父分类/父标签时其子级一并删除，子级关联的时间记录的 categoryId 引用按现有规则处理（级联或明确迁移），无孤儿引用。
- [ ] AC5: 时间记录可挂任意层级分类；标签选择器显示两级结构。
- [ ] AC6: 统计页可在「独立/汇总」两种聚合模式间切换，数字正确（汇总模式下子级时长计入父级）。
- [ ] AC7: 全量测试（server + web build/lint）通过。
